**Data:** 20/11/2026 · **Referência:** requisitos derivados da implementação na árvore de trabalho baseada em `c7d4dad`.

## 1. Convenções de execução e veredicto

Cada CT tem ID único e requisito RF01, RF02 ou RF03. Os preços usam MZN; nos testes de aritmética, os inteiros representam **centavos**. Relógio `t0` significa tempo congelado pelo teste. As contas e dados são sintéticos, gerados por factories; não são credenciais de produção.

- **A — Automatizado:** comportamento/entrada indicado exercitado na suíte corrente; a evidência é o JUnit do ficheiro identificado. O nível pode ser unidade ou componente, não necessariamente interface real.
- **P — Planeado:** o caso exacto ainda não foi executado nesta auditoria, mesmo que exista cobertura próxima. Não conta como aprovado.
- **R — Reprovado no domínio:** comportamento esperado não satisfeito; pode existir teste diagnóstico aprovado que confirma o defeito.
- **C — Cobertura parcial/indirecta:** componentes/fluxo relacionados exercitados, sem prova do CT completo com exactamente os dados e interface descritos.

**Critério geral:** um CT só é aprovado quando o resultado observado coincide com o esperado e as verificações de persistência/ausência de efeitos indevidos se confirmam. Redireccionamentos de formulários com erros de sessão não são HTTP 200 de sucesso. Quando o cliente solicita JSON, a validação pode responder 422; autorização recusada e entidade não visível seguem 403/404 conforme a rota. Não impor o mesmo código HTTP a contratos diferentes.

O relatório `evidencias/regressao-php.xml` contém os nomes dos testes executados; `evidencias/unitarios.xml` isola E3. A coluna de verificação identifica também os casos planeados, para que existência de uma regra no código não seja confundida com teste executado.

## 6. Dados, limpeza e repetibilidade

Os testes automatizados usam factories e uma BD SQLite isolada; o teste concorrente cria um ficheiro temporário próprio. O relógio é controlado onde os limites temporais importam. Os seeders exercitados pelos testes trabalham nessa ligação isolada, não no MySQL publicado. Não incluir palavras-passe, chaves API ou dados de contas reais na matriz.

Para execução manual, preparar um conjunto específico em ambiente de aceitação, conservar referências de operações e registar o estado inicial/final. A limpeza deve limitar-se a esse ambiente descartável. Não usar `migrate:fresh`, truncaturas ou reset do ambiente publicado para repetir um cenário. Depois de uma correcção, repetir o CT reprovado, os casos adjacentes de fronteira e a regressão relevante.
